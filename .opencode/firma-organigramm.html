Singular 80 Software — Organigramm

Wie die Agenten als Firma organisiert sind: Rollen, Menschen, Maschinen, und die zwei Wege, die eine Arbeit vom Vorschlag bis zum Gerät nimmt. Gestrichelt = gibt es noch nicht. Rot = Befund, der heute offen ist.

Die eine Regel: Die Firma besitzt ein Repository, nicht ein Verzeichnis. Jede Arbeit ist ein Zweig, bevor sie eine Änderung ist. Nur die Rolle Release Manager fasst main an, und nur über das Gate.
Aus dieser Regel fallen die meisten Regeln in AGENTS.md von selbst weg: kein git add -A mehr, kein „Tests gehören der Leitsitzung", kein „Parken statt Merge" — geparkt ist bereits alles, und Tests laufen im eigenen Auscheckout.

Die Firma

Oben die Menschen, darunter die Maschinen, darunter die Rollen — und unter jeder Rolle die Menschen, die sie heute besetzen. Die Zuordnung ist Daten, nicht Text: eine Rolle ohne Besetzung ist ein offener Posten, kein fehlendes Dokument.

Developer-Lane

Urteil: gefixt → der Zweig geht ins Gate. Weiter kaputt und Runde < 2 → nächste Developer-Runde. Nach zwei Runden entscheidet ein Mensch. Sonst frisst ein Gerätefehler die ganze Warteschlange.

Personal — austauschbar, Rollen nicht

Heute ist in jeder Agentendatei Rolle und Person in einem Dokument. Deshalb kostet jede neue Fähigkeit eine große Datei, und die gleiche Anweisung wird kopiert und driftet. Getrennt: die Rolle beschreibt den Job, die Person nennt nur Rolle, Schreibtisch und Modell.

Und warum das trägt: eine neue Fähigkeit = eine Rollenkarte + eine kleine Personendatei. Ein anderes Modell = eine Zeile. Eine Rolle fällt weg = Karte löschen, und das Manifest sagt, wen das ohne Job lässt. Und die Regel, die das nicht verhindert: validate() schlägt fehl, wenn eine Person eine Rolle nennt, die es nicht gibt — man kann niemanden in einen Job einstellen, der nicht auf dem Ordner liegt.

Was das Organigramm heute zuerst reparieren muss

Drei Befunde aus dem Abgleich zwischen Manifest, Agentendateien und Code. Alle drei sind keine Vermutung, alle drei stehen in genau einer Datei.

Zwei Schreibtische haben niemanden

scripts/scopes.mjs benennt für lobby, core und tests die Agenten lobby und build — Agentendateien mit diesen Namen existieren nicht. Die Bereiche werden also einem Besitzer zugerechnet, den es nicht gibt, und niemand merkt es, weil die Prüfung nur Eigentümerschaft kennt, nicht Besetzung.

Lösung: Rollen und Personen trennen, und dieselbe Prüfung für beides laufen lassen.

Der Server nennt ein Skript, das es nicht gibt

server/index.ts:36 sagt dem Besitzer nach dem Start: „zusammenführen mit: npm run merge-gate". Das Skript heißt gate. Der Satz erscheint genau dann, wenn die isolierten Läufe an sind — also in dem Moment, in dem jemand das Gate suchen muss.

Einwortkorrektur, aber sie steht im Moment, in dem sie am meisten auffällt.

main kann rot sein, ohne dass irgendetwas es merkt

npm test prüft Content-Sync, Kataloge und Vitest — aber kein typecheck. Ein Lauf, der server/db.ts auf RunRecord.worktreePath schreibt, während src/shared/types.ts das Feld noch nicht kennt, ist grün in npm test und rot in tsc. Das Gate würde es sehen — das Gate ist ein Kommando, das niemand aufruft.

typecheck gehört in npm test. Ein Build, der unbemerkt rot werden kann, ist ein CI, das an nichts angeschlossen ist.

Governance

Das Budget
Eine Einstellung im Dashboard, neben maxParallelRuns.
  • monatliche Obergrenze in derselben Währung, die die Läufe schon führen (RunRecord.cost)
  • ist sie leer, besetzt der Resource Manager niemanden mehr
  • niemand merkt eine fehlende Funktion, alle merken ein leeres Konto
Der Wochenbericht
Vier Zeilen, an den Product Owner. Mehr nicht.
  • was rausging, was blockiert, was es gekostet hat, was fault
  • keine Dateinamen, keine Commit-Hashes, kein Teststatus
  • dieselbe Regel wie im Abschlussbericht: ein Stichpunkt, ein Satz
Der Bereitschaftsdienst
Eine Regel, und sie ist die einzige Ausnahme von der Reihenfolge.
  • ein Vorfall wartet nicht hinter neun Aufgaben
  • der Resource Manager hebt ihn hoch und besetzt sofort
  • die QA-Lane ist ohnehin heiß, der Developer wird an Ort und Stelle eingestellt
Der Einstellungsweg
Einstellen ist eine Personalentscheidung, und sie sieht auch so aus.
  • Postkarte: Rolle, Grund, Kosten, erste Aufgabe — noch kein Agent
  • Probezeit: echte Aufgaben, beurteilt nach Diff, Ehrlichkeit, Schreibtisch
  • Beförderung: dieselbe Person, mehr Verantwortung, ausdrücklich vermerkt
  • Entlassung: eine Fähigkeit, die ihr Geld nicht mehr verdient

Was als Erstes gebaut würde: die Trennung von Rolle und Person samt validate()-Regel. Sie ist klein, sie fasst keinen Laufzeitcode an, und sie ist die Voraussetzung für jede spätere Einstellung — die erste davon ist der Reviewer.

Das Organigramm ist ein Entwurf, kein Zustand. Belegt ist, was oben als „im Dienst" steht; alles Gestrichelte ist Vorschlag. Quelle: .opencode/agents/, scripts/scopes.mjs, server/runner.ts, server/isolation.ts, scripts/merge-gate.mjs, server/checks/.
